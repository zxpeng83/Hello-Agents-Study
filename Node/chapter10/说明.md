# 第十章学习疑惑与解答

本文件整理阅读[第十章 智能体通信协议](<../../hello-agents/docs/chapter10/第十章 智能体通信协议.md>)时的疑惑及讨论结果。

## 1. MCP Server 如何读取本地文件？它不是官方的远程服务吗？

对应教材：**10.2.1 MCP 协议概念介绍**，以及 **10.2.3 MCP 传输方式详解**。

### 疑惑

10.2.1 的那个使用 MCP 请求文件内容的例子不太懂，MCP Server 是如何读取到本地文件内容的？我的理解是 MCP Server 是 MCP 官方的远程服务，那这个远程服务器是如何读取我本地的文件内容的？是我哪里理解错了吗？

### 解答

**（1）MCP Server 是服务端程序，可以在本地或远程运行。**

你主要是把 **“Server（服务端程序）”理解成了“官方部署在云端的服务器”**。在这个例子里，**文件系统 MCP Server 就运行在你的电脑上**，所以它能读取你的本地文件。

MCP Server 指的是“按照 MCP 协议提供工具或数据的程序”，它可以运行在本地，也可以部署到远程。官方文档也明确以 Claude Desktop 的文件系统服务为例，说明它通过 stdio 在同一台电脑上运行。[MCP 架构说明](https://modelcontextprotocol.io/docs/learn/architecture)

**（2）本例中，云端模型与本地的 Host、Client、Server 分工协作。**

实际的位置关系是这样的：

```text
【云端】
    Claude 模型
        ↑↓ 模型请求、工具调用意图、工具结果

【你的电脑】
    Claude Desktop（Host）
        内部包含 MCP Client
        ↑↓ MCP 消息，通过 stdio 传递
    文件系统 MCP Server（本地运行的服务端程序）
        ↑↓ 操作系统的文件读写接口
    本地文件
```

**（3）本地 Server 执行文件读取，模型根据返回的内容生成回答。**

假设你说：“帮我读取 `E:\notes\hello.txt`，总结一下。”在已经配置好文件系统服务、允许访问这个目录的前提下，过程是：

1. **模型决定需要读取文件**，生成工具调用请求，其中包含文件路径。
2. **Claude Desktop 中的 MCP Client**，把请求发给本机运行的文件系统 MCP Server。
3. **MCP Server 执行真正的读取代码**：检查路径是否在允许范围内，再调用文件读取函数。这和你自己写程序使用 Python 的 `open()` 读取文件，是同一类操作。
4. 文件内容返回给客户端，再由宿主应用交给模型，模型据此生成总结。

文件系统 Server 的源码确实就是“校验路径 → 读取文件 → 将内容包装成工具结果返回”这条逻辑。[文件系统 Server 源码](https://github.com/modelcontextprotocol/servers/blob/main/src/filesystem/server.ts)

**（4）`npx` 获取并启动本地服务程序，“官方提供”与运行位置是两回事。**

你往后看到 **10.2.2** 的这段代码，就能把“服务端在哪里”对应起来：

```python
client = MCPClient([
    "npx", "-y",
    "@modelcontextprotocol/server-filesystem",
    "."
])
```

这里的意思是：**通过 `npx` 获取并在本机运行文件系统 MCP Server 程序**，再与它通信。`@modelcontextprotocol/server-filesystem` 是程序包的名字；最后的 `"."` 指定当前目录作为允许访问的目录。官方仓库提供的也是这种本地启动配置。[文件系统 Server 使用说明](https://github.com/modelcontextprotocol/servers/blob/main/src/filesystem/README.md)

因此，**“官方提供了这个程序”与“这个程序运行在哪里”是两回事**。你下载官方提供的软件，软件仍然可以在你的电脑上运行。

**（5）远程 Server 不能仅凭一个本地路径读取你的硬盘。**

如果 MCP Server 确实部署在远程机器上，它直接读取的通常就是**那台远程机器能访问的文件**。要读取你电脑上的内容，还需要额外的上传、文件共享或本地桥接机制；单纯把 `E:\notes\hello.txt` 这个路径发给它，并不能让它访问你的硬盘。

**（6）本例对应 10.2.3 的 Stdio 传输方式，需区分通信与文件读取。**

这个问题在后面的 **10.2.3 MCP 传输方式详解**中有进一步说明，正对应 **（1）表 10.4 中的 Stdio 传输方式**。表格中这一行的描述是：

- **适用场景**：本地开发、命令行工具。
- **优点**：简单、无需网络配置。
- **缺点**：仅限本地、可能有兼容性问题。

后面的 **10.2.3（4）“Stdio Transport—标准输入输出传输”**，还直接演示了通过 `npx` 启动本地文件系统 MCP Server，并调用工具读取 `README.md`。

把它与前面的文件读取例子对应起来，就是：

```text
MCP Client
    │
    │ 通过 stdio 发送读取请求
    ↓
本地文件系统 MCP Server
    │
    │ 调用操作系统的文件读取接口
    ↓
本地文件
```

这里需要分清两个环节：**stdio 解决的是 Client 与 Server 如何传递请求和结果；真正读取文件的是 Server 内部的文件操作代码。** 不是 stdio 本身在读取硬盘。

从章节安排看，**10.2.1 主要介绍 Host、Client、Server 的逻辑职责，没有在那个例子里明确标出 Server 的运行位置**；到了 **10.2.3**，才把本地进程通信和远程服务通信的区别进一步展开。结合这两节，就能理解前面的文件系统 Server 为什么可以读取本地文件。

## 2. 10.2.4 中 MCP 如何与 LLM 协作？能否通过原生 tools 参数传递工具说明？

对应教材：**10.2.4 在智能体中使用 MCP 工具**，关于工具自动展开、Agent 调用工具和智能文档助手的例子；同时联系 **7.4.5 FunctionCallAgent**。

### 疑惑

- 10.2.4 的例子看起来都是代码写死地调用 MCP，实际中是不是应该由 LLM 根据提示词和工具说明决定调用？
- Function Calling 可以把工具描述按一定格式交给 LLM，让 LLM 返回工具名称和参数。MCP 工具又是如何提供给 LLM 的？
- MCP 工具说明是不是只能写进系统提示词，不能使用模型 API 原生的工具参数？如果可以，为什么本章使用 `[TOOL_CALL:...]`？
- 自己编写的函数和 MCP Server 提供的工具，是否都能通过模型 API 的 `tools` 参数传递工具说明？

### 解答

**MCP 工具完全可以通过模型 API 原生的 `tools` 参数传入，并使用原生 Function Calling 机制。** 本章 `SimpleAgent` 展示的“工具说明拼入系统提示词、解析 `[TOOL_CALL:...]` 文本”，不是采用 function calling 的在api传递 tools 参数的机制，是具体的 Agent 提示词自定义规则实现方式，不能推广成 MCP 的限制。

接入 MCP 后，“提供工具描述 → 模型返回调用说明 → 程序执行工具 → 结果交回模型”这个循环依然存在。MCP 主要补充的是“工具描述从哪里获取，以及工具请求如何发送给服务端”这一层。

**（1）代码注册工具，与代码直接指定工具调用，是两个不同阶段。**

10.2.4 中的这几行代码，职责不同：

```python
# 配置工具来源：使用内置的 MCP 演示服务器
mcp_tool = MCPTool(name="calculator")

# 将服务器提供的工具接入 Agent
agent.add_tool(mcp_tool)

# 把任务交给 Agent，内部由 LLM 决定如何处理
response = agent.run("计算 25 乘以 16")
```

这里，开发者指定了“这个 Agent 可以使用哪些工具”，但没有直接在业务代码里指定“调用 `multiply`，参数为 `a=25、b=16`”。

如果直接通过 MCP 客户端调用，代码则可以是这样的，下面以异步客户端为例：

```python
# 明确指定工具和参数，由程序决定执行什么
result = await client.call_tool("multiply", {"a": 25, "b": 16})
```

两种方式都可以使用 MCP：

- **程序直接调用**：业务代码确定工具和参数，适合固定流程、测试等场景。
- **LLM 决定调用**：程序提供可用工具，模型根据任务选择工具和参数。

10.2.4 主要展示第二种方式（指教材中的 `agent.run(...)` 示例；上面的 `client.call_tool(...)` 是补充的直接调用对照示例）。`agent.run(...)` 内部的封装，让它看起来只有一行代码，其实里面是将问题和工具描述发送给llm，然后根据llm返回的工具使用提示调用mcp。

**（2）MCP Server 提供结构化的工具描述，HelloAgents 将工具展开并注册给 Agent。**

连接 MCP Server 后，客户端可以通过 `tools/list` 获取工具列表，其中包括工具名称、功能描述和参数的 JSON Schema。[MCP 工具规范](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)

例如，乘法工具的定义可以是下面这样，这是用于说明结构的示例：

```json
{
  "name": "multiply",
  "description": "计算两个数字的乘积",
  "inputSchema": {
    "type": "object",
    "properties": {
      "a": {"type": "number", "description": "第一个数字"},
      "b": {"type": "number", "description": "第二个数字"}
    },
    "required": ["a", "b"]
  }
}
```

HelloAgents 获得这些信息后，会为服务器中的各个工具创建包装器，注册到 Agent 的工具系统中。这就是 **10.2.4 所说的“自动展开”**。

```text
MCP Server 提供的工具
    multiply
    add
    subtract
        ↓ HelloAgents 展开并添加名称前缀
Agent 可以使用的工具
    calculator_multiply
    calculator_add
    calculator_subtract
```

自动展开和名称前缀属于 HelloAgents 的封装。上面的 `calculator_multiply` 是 Agent 侧使用的名称，服务器上的原始工具名称仍然是 `multiply`。

随后，框架把工具描述、参数要求和调用方式提供给 LLM。因此，不必在示例代码里再手写一遍全部工具说明。

**（3）本章展示的 SimpleAgent 通过提示词约定调用格式，再解析模型输出。**

在本章展示的方式中，框架生成的工具提示可以理解成下面这样的内容，具体措辞以实现为准：

```text
你可以使用以下工具：

工具名称：calculator_multiply
功能：计算两个数字的乘积
参数：a、b，都是数字

需要调用工具时，请使用：
[TOOL_CALL:{tool_name}:{parameters}]

工具结果会返回给你，请根据结果继续回答。
```

用户提出“计算 25 乘以 16”后，假设模型选择使用工具，就可能输出：

```text
[TOOL_CALL:calculator_multiply:a=25,b=16]
```

框架解析这段输出，提取工具名称和参数，再执行相应的工具包装器。可以结合第七章的配套实现理解这个过程：`_get_enhanced_system_prompt()` 拼接工具说明，`_parse_tool_calls()` 解析调用标记，执行后再把结果交给模型。[查看第七章配套实现](../../hello-agents/code/chapter7/my_simple_agent.py)

这里约定的是 **LLM 如何表达调用意图**：工具描述可从 MCP Server 获取，但 `[TOOL_CALL:...]` 返回格式由 Agent 框架规定。Agent 解析模型返回的普通文本，再通过 MCP 执行工具，而不是读取原生 Function Calling 的结构化调用字段。

教材中的具体依据：

- **[第七章 7.4.1 SimpleAgent](<../../hello-agents/docs/chapter7/第七章 构建你的Agent框架.md>)**：`_get_enhanced_system_prompt()` 将工具描述和调用格式加入系统提示词；`_run_with_tools()` 调用 LLM 后，由 `_parse_tool_calls()` 用正则解析标记，再通过 `_execute_tool_call()` 执行并回填结果。
- **[第十章 10.2.4（1）、（2）](<../../hello-agents/docs/chapter10/第十章 智能体通信协议.md>)**：先给出 `[TOOL_CALL:calculator_multiply:a=25,b=16]` 示例，再说明工具包装器如何把工具名称和参数转换为 MCP 调用。第七章展开模型交互机制，第十章说明如何接入 MCP 工具。

以乘法工具为例，从准备到执行的完整过程如下：

```text
准备阶段
MCP Server 提供工具名称、描述、参数定义
    ↓ MCP Client 获取工具列表
HelloAgents 创建工具包装器、注册工具
    ↓ 构造工具说明和调用格式要求
将这些信息提供给 LLM


执行阶段
用户：“计算 25 乘以 16”
    ↓
LLM 根据任务和工具描述，选择乘法工具
    ↓ 输出调用意图
[TOOL_CALL:calculator_multiply:a=25,b=16]
    ↓
HelloAgents 解析工具名称和参数
    ↓
工具包装器找到对应的 MCP Server
将 calculator_multiply 映射回 multiply
将参数整理为 {"a": 25, "b": 16}
    ↓
MCP Client 发送 tools/call 请求
    ↓
MCP Server 执行 multiply，返回结果 400
    ↓
HelloAgents 将工具结果加入对话，再调用 LLM
    ↓
LLM 回答：“25 乘以 16 的结果是 400。”
```

模型通常只需要知道“有哪些工具、工具有什么用、参数是什么、如何表达调用意图”。启动服务的 `npx` 命令、stdio 通信和 MCP 消息封装，由应用程序处理。

**（4）MCP 工具可以接入原生 Function Calling，工具说明同样可以放进 tools 参数。**

MCP 官方的客户端教程就在使用模型 API 原生的工具参数：先从 MCP Server 获取工具定义，再转换成模型 API 接受的格式，通过 `tools` 参数传入模型；模型返回结构化的工具调用后，再通过 MCP 执行。[MCP 官方客户端教程](https://modelcontextprotocol.io/docs/develop/build-client)

以该教程使用的 Claude API 为例，核心转换可以写成下面这样。这里的 `mcp_tool_definition` 指从 MCP 获得的工具定义字典；代码展示核心片段，省略客户端初始化等部分：

```python
# 将 MCP 工具定义转换成模型 API 接受的格式
native_tool = {
    "name": mcp_tool_definition["name"],
    "description": mcp_tool_definition["description"],
    "input_schema": mcp_tool_definition["inputSchema"],
}

# 通过原生 tools 参数传入，不需要把工具定义拼进系统提示词
response = model_client.messages.create(
    model=model_name,
    max_tokens=1024,
    messages=messages,
    tools=[native_tool],
)
```

模型返回原生的 `tool_use` 调用信息，包括工具名称和参数。应用再取出这些信息，调用 MCP Client 执行工具，并把结果交回模型继续生成。

因此，在我们讨论的、提供 `tools` 参数的模型 API 中，两类工具都可以通过 `tools` 传递工具说明：

| 工具来源              | 工具说明如何提供给模型                                         | 模型返回调用后，如何执行             |
| --------------------- | -------------------------------------------------------------- | ------------------------------------ |
| 自己编写的函数        | 将函数描述和参数定义放进 `tools`                             | 应用调用对应函数                     |
| MCP Server 提供的工具 | 获取 MCP 工具定义，转换成模型 API 要求的格式，再放进 `tools` | 应用通过 MCP Client 请求 Server 执行 |

更准确地说，**MCP 工具也可以使用模型原生的 Function Calling 机制**。`tools` 是模型 API 的参数；MCP 提供工具发现和调用接口，应用负责把两边连接起来。

对模型 API 来说，这个工具的后端是本地 Python 函数，还是 MCP Server 提供的能力，并不影响它接收工具声明和生成调用参数。

原生 Function Calling 支持的是“工具声明与结构化调用”这种机制，并不需要提前把每一个工具的实际实现内置到模型里。新增一个 MCP 工具，也不意味着模型厂商要为它新增一种 API。

**（5）模型工具调用与 MCP 通信处于不同层，不能混淆各层的消息格式。**

Function Calling 与 MCP 对接的是两段不同的通信：

```text
LLM
    ↑↓ 模型 API 的原生工具定义、结构化工具调用
Agent 应用 / Host
    ↑↓ MCP 的工具发现、工具调用、执行结果
MCP Server
    ↓
实际工具实现
```

Agent 应用负责连接两边：从 MCP Server 获取名称、描述、参数 Schema，转换为模型 API 接受的工具定义；再将模型返回的调用信息转换成 MCP 工具调用，最后将执行结果交回模型。

教材中的以下字典，属于 **HelloAgents 包装器使用的接口格式**：

```python
{
    "action": "call_tool",
    "tool_name": "multiply",
    "arguments": {"a": 25, "b": 16}
}
```

需要区分以下几种格式：

| 所处层面                         | 示例格式                                                  | 谁负责处理                          |
| -------------------------------- | --------------------------------------------------------- | ----------------------------------- |
| 本章 SimpleAgent 与模型之间      | `[TOOL_CALL:calculator_multiply:a=25,b=16]`             | Agent 解析模型生成的文本            |
| 原生 Function Calling 的模型接口 | API 规定的结构化工具调用，例如 Claude 的 `tool_use`     | 应用读取工具名称和参数              |
| HelloAgents 工具包装接口         | `{"action": "call_tool", "tool_name": "multiply", ...}` | 包装器转换为相应的 MCP 调用         |
| MCP 协议层                       | JSON-RPC 请求的方法名 `tools/call`                      | MCP Client 与 MCP Server 按协议交互 |

前两行是不同的模型调用接入方式，并不是每次调用都必须依次经过的两个阶段。**`[TOOL_CALL:...]` 是教程框架与模型之间的文本约定，不是 MCP 协议规定的格式，也不等同于模型 API 原生的 Function Calling。**

MCP 统一的是应用与工具服务之间的交互，模型侧使用哪一种调用机制，由应用和框架选择。MCP 官方也明确说明，协议本身不规定应用如何使用 LLM、如何管理提供给模型的上下文。[MCP 架构说明](https://modelcontextprotocol.io/docs/learn/architecture)

**（6）本章的提示词方案与原生 Function Calling，是不同的 Agent 实现方式。**

同一个 MCP 工具，可以通过不同方式提供给模型：

| 环节             | 本章展示的提示词方式             | 原生 Function Calling 方式                         |
| ---------------- | -------------------------------- | -------------------------------------------------- |
| 获取工具定义     | 从 MCP Server 获取               | 从 MCP Server 获取                                 |
| 提供给模型       | 将工具描述和调用格式写入提示词   | 转换成模型 API 接受的工具定义，通过 `tools` 传入 |
| 模型返回调用意图 | `[TOOL_CALL:...]` 文本         | API 规定的结构化工具调用                           |
| 执行工具         | 框架解析后，通过 MCP Client 调用 | 框架解析后，通过 MCP Client 调用                   |
| 处理结果         | 把结果交回模型继续生成           | 把结果交回模型继续生成                             |

变化发生在 **Agent 与模型之间**，MCP 服务端提供工具的机制可以保持不变。

本地教材里也有明确的版本线索：

- 第十章指定安装 `hello-agents[protocol]==0.2.2`，并展示 `[TOOL_CALL:...]`。
- 第七章 **7.4.5 FunctionCallAgent** 标注，该 Agent 在 **0.2.8 之后引入**，示例已经通过原生 `tools=tools` 传递工具定义。

这反映了教材中不同阶段的 Agent 实现，不能把某个示例采用的调用方式，当成整个 MCP 生态的能力上限。这里的版本对照用于理解实现差异，并不表示直接替换第十章的 Agent 就能保证示例兼容。[查看第七章教材](<../../hello-agents/docs/chapter7/第七章 构建你的Agent框架.md>)

**（7）使用原生 tools 参数时，系统提示词仍可以指导“什么时候调用”。**

例如，可以在系统提示词中写：

> 回答涉及文件实际内容的问题时，先读取文件，再根据读取结果回答。

同时，把读取文件工具的名称、参数类型和必填字段，通过原生 `tools` 参数传入。

这两者承担不同职责：**提示词指导行为策略，工具定义描述可调用的能力及参数格式；MCP 负责连接和执行工具服务。** 使用原生工具参数，不等于不再需要系统提示词；系统提示词也不必承担完整描述工具接口的工作。

**（8）文档助手案例确实混合了固定流程、LLM 决策和普通文件写入。**

10.2.4（3）的智能文档助手，并不是每一步都由 LLM 自主决定，也不是每一步都经过 MCP：

- **先搜索，再生成报告**：由 Python 代码确定执行顺序。
- **搜索 Agent 使用什么工具、传什么查询参数**：由其内部的 LLM 根据任务和工具说明决定。
- **最后保存 `report.md`**：示例直接使用 Python 的 `open()` 写入，并不是由 LLM 调用文件系统 MCP 工具完成。

示例给文档生成 Agent 的提示词还明确写了“请直接输出完整的 Markdown 格式报告内容，不要使用工具保存”。因此，虽然代码注册了文件系统 MCP 工具，也不能据此认为实际保存报告时调用了它。[查看文档助手配套代码](../../hello-agents/code/chapter10/06_MultiAgentDocumentAssist.py)

需要分别判断外层流程由谁编排、内部工具由谁选择，以及最终操作通过什么代码执行。外层流程由 Python 固定，并不意味着内部的工具选择和参数也全部写死了。


## 3. MCP 是为了适配 OpenAI 的 tools 参数而设计的吗？

对应教材：**10.2.1 MCP 协议概念介绍**中关于 MCP 与 Function Calling 的差异，以及 **10.2.4 在智能体中使用 MCP 工具**。

### 疑惑

LLM API 的 `tools` 参数最初是设计给符合 OpenAI 格式的 Function Calling 用的，后来 Anthropic 设计了 MCP，是其主动去适配 OpenAI 格式的 `tools` 参数的。这样理解对吗？

### 解答

不完全对。**你理解对了“接入时需要适配格式”，但适配通常由应用或框架完成；MCP 本身并不是专门按照 OpenAI 的 `tools` 格式设计的。**

我前面说“都可以用 `tools` 参数”，还需要补充一个限定：**参数同名，不代表里面的数据格式相同。**

**（1）不同厂商有各自的模型 API，`tools` 并不是统一的 OpenAI 格式。**

以我们讨论的接口为例：

| 接口或协议 | 工具定义中的典型字段 |
| --- | --- |
| OpenAI Chat Completions 的函数工具 | `type: "function"`，内部 `function` 包含 `name`、`description`、`parameters` |
| Claude API 的工具 | `name`、`description`、`input_schema` |
| MCP 的工具定义 | `name`、`description`、`inputSchema` |

OpenAI 和 Claude 都有叫 `tools` 的参数，但接收的结构不同。MCP 又有自己的工具定义格式。[OpenAI 官方文档](https://developers.openai.com/api/docs/guides/function-calling)、[Claude 工具定义](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)、[MCP 工具规范](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)

因此，不能把“LLM API 的 `tools` 参数”理解成所有模型都遵守的一个 OpenAI 接口。

**（2）MCP 的目标是统一工具服务的接入，而不是统一成 OpenAI 的模型 API。**

Anthropic 在 2024 年 11 月发布 MCP 时，说明的目标是统一 AI 应用与数据源之间的连接，减少每接入一个数据源就单独开发集成的工作。[MCP 发布公告](https://www.anthropic.com/news/model-context-protocol)

它允许同一个工具服务被不同应用、不同模型使用。因此，MCP 工具定义保持独立，接入哪一种模型 API，再转换成对应格式。

**（3）你说的“适配”，实际可以这样理解。**

```text
MCP Server 提供工具定义
    name、description、inputSchema
                  ↓
          Agent 应用 / 框架转换
                  ↓
    ┌─────────────┴─────────────┐
    ↓                           ↓
OpenAI API                  Claude API
tools 参数                  tools 参数
按 OpenAI 要求组织          按 Claude 要求组织
使用 parameters             使用 input_schema
```

如果使用 OpenAI API，应用就转换成 OpenAI 格式；如果使用 Claude API，就转换成 Claude 格式。

**MCP 官方客户端教程本身就展示了“MCP 工具 → Claude 原生工具格式 → Claude 的 `tools` 参数”的过程，中间并不需要经过 OpenAI 格式。**[官方客户端教程](https://modelcontextprotocol.io/docs/develop/build-client)

**（4）OpenAI 早期的函数调用参数名称，也经历过变化。**

另外，“OpenAI 最初就是使用 `tools` 参数”这个历史细节也要修正：其早期函数调用接口使用 `functions` 和 `function_call`，后来分别由 `tools` 和 `tool_choice` 替代；官方接口文档仍列出了这些弃用关系。[OpenAI 接口文档](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)


## 4. 10.3.3 和 10.3.4 是否省略了 LLM 选择工具的过程？

对应教材：**10.3.3 使用 HelloAgents A2A 工具**、**10.3.4 在智能体中使用 A2A 工具**。

### 疑惑

在 10.3.3 和 10.3.4 的例子中，是不是都没体现 LLM 回复提示使用哪个 MCP 工具的过程？是略过了，还是不需要？

### 解答

**这两节的情况不同：10.3.3 是程序直接指定调用；10.3.4（1）（2）有 LLM 决策，但封装在 `SimpleAgent.run()` 内部。**

另外，这里更准确地说是 **A2A 工具（`A2ATool`）**，不是 MCP 工具。两者都能接入 HelloAgents 的工具系统，所以使用形式很像，但底层通信协议不同。

**（1）10.3.3：没有 LLM 决定调用哪个工具，这个示例不需要它。**

例如：

```python
response = client.execute_skill(
    "research",
    "research AI在医疗领域的应用"
)
```

这里的技能名称 `"research"` 和请求内容，都由程序直接指定。

后面的研究员、撰写员、编辑协作，也是代码固定编排：

```text
程序调用 research
    ↓
程序将研究结果交给 write
    ↓
程序将文章交给 edit
```

服务端的处理函数也只是解析文本、拼接演示结果，没有调用 LLM。

因此，这里**不是隐藏了 LLM 的选择过程，而是示例本身没有这个过程**。它主要演示客户端如何访问服务端、如何串联多个服务。[教材 10.3.3](<../../hello-agents/docs/chapter10/第十章 智能体通信协议.md#1033-使用-helloagents-a2a-工具>)

**（2）10.3.4（1）（2）：有 LLM 选择工具的过程，只是教材没有展开中间响应。**

例如协调者：

```python
coordinator = SimpleAgent(name="协调者", llm=llm)
coordinator.add_tool(researcher_tool)

response = coordinator.run(
    "请让研究员帮我研究AI在教育领域的应用"
)
```

这里已经引入 `llm`，并把 A2A 工具注册给 `SimpleAgent`。`run()` 内部负责组织工具说明、调用模型、解析工具调用并执行。

客服例子更容易看出这种选择。假设用户问：

> 企业版的价格是多少？

按示例的设计，预期流程是：

```text
用户问题
    ↓
接待员 SimpleAgent 将问题和工具说明交给 LLM
    ↓
LLM 判断这是价格问题
    ↓
生成调用 sales_advisor 的工具调用信息
    ↓
Agent 解析后，执行对应的 A2ATool
    ↓
通过 A2A 请求销售顾问服务
    ↓
销售顾问返回结果
    ↓
接待员 LLM 整理结果，回答用户
```

**LLM 回复“应该调用哪个工具”的过程，发生在 `receptionist.run(query)` 内部。** 示例只写了这个入口，没有把模型的中间响应逐步展开。[教材 10.3.4](<../../hello-agents/docs/chapter10/第十章 智能体通信协议.md#1034-在智能体中使用-a2a-工具>)

不过，要区分调用方和服务方：**接待员使用了 LLM，但示例中的技术专家、销售顾问服务端仍然只是返回模板文本。** 教材也注明了“实际应用中，这里会调用 LLM 或知识库”。所以不能认为示例中每个被称为 Agent 的服务，都已经具备模型推理能力。

**（3）10.3.4（3）的“Agent 间协商”：又是一个没有 LLM 的简化示例。**

它使用的是：

```python
if deadline >= 7:
    # 接受提案
else:
    # 提出至少需要 7 天
```

这是固定规则判断。另一个 `negotiate_task()` 也只是构造并返回提案，代码没有展示真正发给另一方、接收答复、继续协商的完整往返。[协商示例：10.3.4（3）](<../../hello-agents/docs/chapter10/第十章 智能体通信协议.md#1034-在智能体中使用-a2a-工具>)

因此，这一小节也没有“LLM 选择工具”的过程。**A2A 提供通信机制；调用什么、怎样处理请求，可以由业务代码决定，也可以交给 LLM。**


## 5. 10.5 的天气 MCP 服务使用哪种传输方式？发布版改为 HTTP 的代码在哪里？

对应教材：**10.2.3（1）传输方式概览**中的表 10.4，以及 **10.5.1 创建你的第一个 MCP 服务器**、**10.5.2 上传 MCP 服务器**。

### 疑惑

- 10.5 的天气 MCP 服务，对应表 10.4 中的哪种传输方式？
- “10.5.2 发布用的配套代码改成了 HTTP 传输”，具体体现在哪里？为什么只看正文不容易发现？

### 解答

**10.5.1 中本地运行、测试天气服务的例子，对应表 10.4 的 Stdio（标准输入输出）传输。** 后面 10.5.2 的发布版本则做了调整，需要分开看。

**（1）10.5.1：通过 Stdio 连接本地天气 MCP 服务。**

判断依据是客户端这样连接：

```python
client = MCPClient(["python", server_script])
```

在 Agent 中也是：

```python
weather_tool = MCPTool(
    server_command=["python", server_script]
)
```

这表示：**客户端启动一个本地 Python 服务进程，通过标准输入、标准输出与它交换 MCP 消息。** 和前面通过 `npx` 启动文件系统服务属于同一种传输方式，只是启动的程序不同。[天气助手配套代码](../../hello-agents/code/chapter10/14_weather_agent.py)

对应的服务端文件 [14_weather_mcp_server.py](../../hello-agents/code/chapter10/14_weather_mcp_server.py) 第 76 行，使用默认方式启动：

```python
weather_server.run()
```

**（2）天气服务内部访问 HTTPS 网站，不代表 MCP 连接使用 HTTP 传输。**

天气服务内部确实使用了下面这样的请求，这里省略了具体城市路径：

```python
requests.get("https://wttr.in/...", timeout=10)
```

但这是**天气服务去查询外部天气数据**，不是 MCP Client 与 MCP Server 之间的传输方式：

```text
Agent / MCP Client
    ↑↓ Stdio：传递 MCP 请求和结果
本地天气 MCP Server
    ↑↓ HTTPS：查询天气数据
wttr.in 天气网站
```

**表 10.4 讨论的是上面第一段连接，不是第二段。**

**（3）10.5.2：发布目录中的 server.py 显式设置了 HTTP 传输。**

具体位置在配套文件 **[code/chapter10/weather-mcp-server/server.py](../../hello-agents/code/chapter10/weather-mcp-server/server.py) 第 88 行**：

```python
weather_server.run(transport="http", host=host, port=port)
```

这里明确指定了 `transport="http"`，改为通过网络地址提供 MCP 服务。它与 10.5.1 中的 `14_weather_mcp_server.py` 是两个不同的文件，启动参数也不同。

按底层 FastMCP 的命名，`transport="http"` 使用的是 **Streamable HTTP**，因此更准确地对应表中的 **StreamableHTTP**。[FastMCP 传输说明](https://gofastmcp.com/deployment/running-server#http-transport-streamable)

| 例子 | 对应传输方式 |
| --- | --- |
| 10.5.1：客户端用 `python` 命令启动本地天气服务 | **Stdio** |
| 10.5.2：发布目录中显式设置 `transport="http"` 的服务 | **Streamable HTTP** |

同一套天气查询工具，可以采用不同的传输方式；**要看服务如何启动、客户端如何连接，不能仅凭它的功能或是否访问互联网来判断。**

**（4）10.5.2 正文没有重新贴出发布版 server.py 的完整实现，只展示了目录和相关配置。**

教材指出，发布目录已经放在 `code` 中，并展示了 `smithery.yaml` 配置，其中写了：

```yaml
startCommand:
  type: http
```

这段配置位于[第十章教材](<../../hello-agents/docs/chapter10/第十章 智能体通信协议.md>)第 2178 行开始的位置；配套文件 [weather-mcp-server/smithery.yaml](../../hello-agents/code/chapter10/weather-mcp-server/smithery.yaml) 的第 20 行也能看到。

所以，“发布用的配套代码改成了 HTTP”的直接依据，是**发布目录里的 `server.py` 第 88 行**。如果只看正文里的 Python 示例，确实不容易发现这处变化，需要结合配套文件对照阅读。

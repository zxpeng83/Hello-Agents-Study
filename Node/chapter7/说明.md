# 第七章学习疑惑与解答

本文件整理阅读[第七章 构建你的智能体框架](<../../hello-agents/docs/chapter7/第七章 构建你的Agent框架.md>)时的疑惑及讨论结果。

## 1. 如何理解 7.2.2“本地模型调用”，以及它与 LLM、Agent 的关系？

对应教材：**7.2.2 本地模型调用**，并联系第三章使用 Transformers 运行模型的方式、第四章的 `HelloAgentsLLM` 封装与 ReAct 流程。

### 疑惑

- 能否结合一个具体例子，总体解释 7.2.2“本地模型调用”？
- 它与之前章节学习的 LLM、`HelloAgentsLLM`、Agent 有什么关系？
- Ollama、vLLM 分别负责什么？为什么既要运行模型服务，又要创建 `HelloAgentsLLM`？
- 模型从云端换到本机后，Agent 的执行流程是否也会改变？

### 解答

**（1）本节讨论的是把模型运行位置从云端换到本机，并继续让 Agent 调用它。**

7.2.2 讲的是：把“运行在别人服务器上的模型”，换成“运行在自己电脑上的模型”，然后继续让之前的 Agent 调用它。

用一个具体例子串起来：**你有一个计算助手，用户问它“15 × 8 + 32 等于多少？”**

先把几个角色分清：

| 角色                            | 在这个例子中负责什么                                     |
| ------------------------------- | -------------------------------------------------------- |
| **LLM，例如 Qwen、Llama** | 理解问题、生成工具调用指令或最终回答                     |
| **Ollama / vLLM**         | 加载模型，让模型实际运行起来，并提供调用接口             |
| **`HelloAgentsLLM`**    | 把消息发送给模型服务，再接收返回结果                     |
| **Agent**                 | 组织整个办事流程：准备消息、调用 LLM、执行工具、处理结果 |

特别注意：**`HelloAgentsLLM` 是你写的客户端类，它本身不是那个训练好的大模型。**

**（2）调用云端模型与本地模型时，各个角色的分工。**

以前调用云端模型时，关系是：

```text
Agent
  ↓
HelloAgentsLLM
  ↓ 发送请求
厂商的模型服务
  ↓
厂商机器上的 Qwen 等模型
```

模型怎样加载、用哪张显卡计算、怎样处理很多人的请求，都是厂商负责的。你的程序只需要知道 API 地址、模型名和密钥。

到了 7.2.2，你开始自己提供这个模型服务：

```text
你的电脑
┌──────────────────────────────────┐
│ Agent                            │
│   ↓                              │
│ HelloAgentsLLM                   │
│   ↓ 请求 localhost               │
│ Ollama 服务                      │
│   ↓                              │
│ 本机的 Llama 模型                 │
└──────────────────────────────────┘
```

这就解释了本节为什么要分成“运行模型”和“连接模型”两步。

**（3）第一步：用 Ollama 把模型运行起来。**

按照教材例子，在安装并启动 Ollama 后执行：

```bash
ollama run llama3
```

Ollama 负责准备并运行 `llama3` 模型。你可以把这个过程理解为：**让自己电脑上的模型开始提供服务。**

**（4）第二步：让客户端连接这个模型服务。**

```python
llm = HelloAgentsLLM(
    provider="ollama",
    model="llama3",
    base_url="http://localhost:11434/v1",
    api_key="ollama"
)
```

这几项合起来的意思是：

> 后面的问题，请发给我自己电脑上 `11434` 端口的 Ollama 服务，让它使用 `llama3` 回答。

`localhost` 就是当前电脑。这里的 `api_key="ollama"` 是本地接口使用的占位值，Ollama 会忽略它。参考：[Ollama 官方示例](https://docs.ollama.com/api/openai-compatibility#local-server-usage)。

然后，把这个 `llm` 对象传给之前的 Agent。**Agent 仍然通过 `HelloAgentsLLM` 联系模型，只是请求的目的地换了。**

**（5）结合计算器例子，理解 Agent、客户端、模型服务与模型如何协作。**

回到“15 × 8 + 32”这个例子。假设你使用第四章学过的 ReAct 流程，并且注册了计算器工具，一次可能的执行过程是：

1. **Agent 准备消息**：告诉模型用户的问题，以及有哪些工具可用。
2. **`HelloAgentsLLM` 发送消息**：把这些内容发送给本机 Ollama。
3. **本地 Llama 生成指令**：例如要求使用计算器计算 `15*8+32`。
4. **Agent 执行计算器**：得到 `152`。真正调用工具的是 Agent 的 Python 代码。
5. **Agent 再次调用 LLM**：把计算结果传给模型，由模型生成“计算结果是 152”这样的最终回答。

模型也可能直接回答这个简单算式；上面是用来展示工具调用关系的示例。

你可以看到，**ReAct 的步骤没有因为模型搬到本机而改变**。本地运行模型这件事，由 Ollama 承担；组织工具调用这件事，仍然由 Agent 承担。

**（6）与第三章使用 Transformers 的方式有什么关系？**

第三章使用 **Transformers** 时，是由你写的 Python 程序直接加载模型、调用模型生成结果。本节则把模型运行工作交给一个独立服务：

```text
第三章的方式：
Python 程序 → Transformers → 模型计算

本节的方式：
Agent → HelloAgentsLLM → Ollama / vLLM 服务 → 模型计算
```

**（7）vLLM 是另一种运行模型、提供服务的方案。**

文中的 vLLM 命令加载 Qwen，并在 `8000` 端口提供接口；随后客户端连接 `http://localhost:8000/v1`。它和 Ollama 示例采用的是同一种分工。

**（8）PagedAttention、连续批处理属于模型服务内部的运行优化。**

至于 **PagedAttention、连续批处理**，是在解释 vLLM 怎样高效运行模型：

- **PagedAttention**：更有效地存放生成过程中需要的缓存，减少显存浪费。
- **连续批处理**：合理安排多个请求一起计算，提高整体处理效率。

这些优化发生在**模型运行服务这一层**；前几章学到的提示词组织、ReAct 循环、工具执行，发生在 **Agent 这一层**。

## 2. 第七章开发的是 Agent 框架还是 Agent 应用？它与第四章、第六章有什么关系？

对应教材：**7.1 框架整体架构设计**、**7.3 框架接口实现**、**7.4 Agent 范式的框架化实现**、**7.5 工具系统**，并联系[第四章 智能体经典范式构建](<../../hello-agents/docs/chapter4/第四章 智能体经典范式构建.md>)与[第六章 框架开发实践](<../../hello-agents/docs/chapter6/第六章 框架开发实践.md>)。

### 疑惑

- 第七章开发的是 Agent 框架，还是 Agent 应用？
- 第七章与第六章、第四章有什么关系？
- 为什么第四章已经写过 Agent，第七章还要再写？
- 第六章的“框架开发实践”与第七章的“构建你的智能体框架”，分别在做什么？

### 解答

**（1）第七章的主线是开发 Agent 框架，同时用简单的 Agent 应用来演示和验证框架。**

Agent 框架与 Agent 应用的区别，在于解决的问题：

| 比较点   | Agent 框架                                       | Agent 应用                             |
| -------- | ------------------------------------------------ | -------------------------------------- |
| 目标     | 提供构建各种 Agent 的通用能力                    | 完成某个具体任务                       |
| 关注点   | 怎样调用模型、管理消息、执行工具、组织执行流程   | 怎样查天气、规划旅行、回答业务问题     |
| 本章例子 | `Agent` 基类、`ReActAgent`、`ToolRegistry` | 实例化一个助手，让它搜索信息或计算算式 |

例如，你写的 `MyReActAgent` 可以接不同模型、注册不同工具、处理不同问题，因此属于**通用框架组件**。

当你用它搭配天气查询工具，设置旅游规划提示词，做出一个“旅行助手”时，就是在**使用框架开发应用**。

**（2）第七章采用了“使用已有框架、实现或扩展组件、通过应用示例验证”的教学方式。**

第七章容易让人混淆，是因为它采用了这样的教学方式：

```text
安装已有的 hello-agents 框架
          ↓
理解其设计，通过继承实现或扩展组件
          ↓
创建具体助手，运行示例验证组件
```

所以，更准确地说，你在这一章学习的是**框架设计与组件实现**。它也包含应用示例，但没有围绕某个完整业务应用展开开发。

**（3）第四章、第六章、第七章构成了一条连续的学习路线。**

这三章的关系是：**第四章理解 Agent 的内部逻辑，第六章学习使用现成框架，第七章学习构建自己的框架。**

| 章节             | 主要在做什么                                        | 重点回答的问题                             |
| ---------------- | --------------------------------------------------- | ------------------------------------------ |
| **第四章** | 用 Python 实现 ReAct、Plan-and-Solve、Reflection    | Agent 内部究竟怎样运行？                   |
| **第六章** | 使用 AutoGen、AgentScope、CAMEL、LangGraph 开发应用 | 别人的框架怎样帮助我们开发 Agent？         |
| **第七章** | 将通用能力组织成 HelloAgents 框架                   | 怎样把这些能力设计成可复用、可扩展的组件？ |

用“开发一个能够搜索信息的助手”来对比，就更容易理解。

**（4）在第四章，你主要是在亲手写执行逻辑。**

例如 ReAct 的流程：

```text
准备提示词
    ↓
调用 LLM
    ↓
解析模型输出的 Action
    ↓
执行搜索工具
    ↓
把搜索结果交给模型
    ↓
继续循环，直到模型给出最终答案
```

你需要自己实现循环、输出解析、工具执行和停止条件。这样可以看清：**Agent 是怎样围绕 LLM 和工具运转的。**

**（5）在第六章，你使用现成框架提供的组件来构建应用。**

框架已经提供消息、模型调用、工具管理、工作流或多 Agent 协作等能力。你重点设计：

- 助手有哪些角色和职责。
- 使用什么模型、工具和提示词。
- 各个步骤或 Agent 怎样协作。

例如，教材用 AutoGen 构建软件开发团队，用 AgentScope 构建狼人杀游戏。第六章的“框架开发实践”，主要指的是**利用框架开发应用**。

**（6）在第七章，你开始把多个助手都需要的能力设计成公共组件。**

第七章开始思考：如果要支持很多不同的助手，哪些代码应该变成公共组件？

比如，搜索助手和计算助手都需要调用模型、管理消息、执行工具，就可以把这些能力统一起来：

```text
HelloAgents 框架
├── HelloAgentsLLM：统一联系模型
├── Message：统一消息格式
├── Agent：规定通用接口
├── ReActAgent：提供可复用的 ReAct 流程
└── ToolRegistry：统一注册和执行工具
```

以后创建搜索助手，就给 `ReActAgent` 配搜索工具；创建计算助手，就配计算工具。核心执行流程可以复用。

**（7）第四章和第七章看起来有重复，是因为第七章进一步系统化了第四章的实现。**

第四章让你实现一种 Agent 的运行机制，第七章把这些机制进一步整理为共享基础组件、遵循统一接口的框架实现。

第四章也有封装和复用，第七章是在此基础上进一步系统化。

**（8）Agent 范式与 Agent 框架是不同的概念，第七章也不是继续继承第六章介绍的框架。**

**ReAct 是一种执行范式，LangGraph、HelloAgents 是框架。** 范式描述“怎样组织处理过程”，框架提供实现这些过程的代码和接口。

第七章借鉴第六章展示的框架设计经验，但并不是继续继承 AutoGen、LangGraph 等框架来实现 HelloAgents。

## 3. SimpleAgent 是否继承 Agent？这个继承关系在哪里体现？

对应教材：**7.3.3 Agent 抽象基类**、**7.4.1 SimpleAgent**，并对照教材指定的 `hello-agents==0.1.1` 所对应的框架源码。

### 疑惑

- 7.4.1 的 `SimpleAgent` 是不是继承了 7.3.3 讲解的 `Agent`？
- 为什么教材里只看到 `class MySimpleAgent(SimpleAgent)`，没有看到 `class SimpleAgent(Agent)`？
- `SimpleAgent` 继承 `Agent` 的关系具体写在哪个文件、哪一行？

### 解答

**（1）需要区分 Agent、SimpleAgent 和 MySimpleAgent 三个类。**

这一章的继承关系是：

```text
Agent                     ← 7.3.3 讲解的抽象基类
  └── SimpleAgent         ← 框架提供的具体实现
        └── MySimpleAgent ← 7.4.1 中自己编写的子类
```

7.4.1 实际写的是：

```python
from hello_agents import SimpleAgent

class MySimpleAgent(SimpleAgent):
    ...
```

所以，**`MySimpleAgent` 直接继承 `SimpleAgent`，间接继承 `Agent`。**

这三层分别负责：

| 类                | 作用                                                             |
| ----------------- | ---------------------------------------------------------------- |
| `Agent`         | 保存名称、LLM、配置、历史消息等公共信息，并要求子类实现`run()` |
| `SimpleAgent`   | 实现基本的对话逻辑，让抽象的 Agent 变成可以运行的具体智能体      |
| `MySimpleAgent` | 在已有实现上重写、扩展行为，例如本节中的工具调用和流式对话       |

因此，`MySimpleAgent` 可以使用继承而来的 `self._history`、`add_message()`、`get_history()` 等能力，不必重新编写。

**（2）SimpleAgent 继承 Agent 的声明，在框架源码中。**

教材对应的官方 **`V0.1.1` 版本源码**中，[`hello_agents/agents/simple_agent.py` 第 5 行](https://github.com/jjyaoao/HelloAgents/blob/V0.1.1/hello_agents/agents/simple_agent.py#L5) 导入了框架内部的 `Agent`，而[第 9 行](https://github.com/jjyaoao/HelloAgents/blob/V0.1.1/hello_agents/agents/simple_agent.py#L9) 明确声明了继承关系：

```python
from ..core.agent import Agent

class SimpleAgent(Agent):
    ...
```

**`class SimpleAgent(Agent)` 中括号里的 `Agent`，就是直接声明它的父类。**

这里的 `Agent` 来自框架包内部的 `hello_agents/core/agent.py`；7.3.3 展示的是这一层抽象基类的设计。它不是由学习目录中任意一个同名的 `Agent` 类自动替换的。

**（3）SimpleAgent 的构造方法还会调用 Agent 的初始化方法。**

同一个源码文件的[第 19 行](https://github.com/jjyaoao/HelloAgents/blob/V0.1.1/hello_agents/agents/simple_agent.py#L19) 写着：

```python
super().__init__(name, llm, system_prompt, config)
```

在 `SimpleAgent` 的这个方法中，它调用的是 `Agent` 的初始化方法，由基类完成名称、模型、系统提示词、配置和历史记录等公共属性的初始化。

教材中 `MySimpleAgent` 的构造方法也写了 `super().__init__(...)`。在这条单继承链上，初始化的调用关系是：

```text
MySimpleAgent.__init__()
          ↓ super().__init__(...)
SimpleAgent.__init__()
          ↓ super().__init__(...)
Agent.__init__()
```

也就是说，`MySimpleAgent` 先调用 `SimpleAgent` 的初始化方法，再由 `SimpleAgent` 调用 `Agent` 的初始化方法。

**（4）教材省略了框架内部 SimpleAgent 的定义，所以只读 7.4.1 看不到中间那一层声明。**

7.4.1 通过下面这行代码，直接导入安装包中已经实现的 `SimpleAgent`：

```python
from hello_agents import SimpleAgent
```

随后才定义自己的 `MySimpleAgent`。将教材示例和框架源码放在一起，完整关系是：

```text
框架源码：class Agent(ABC)
              ↑
框架源码：class SimpleAgent(Agent)
              ↑
教材示例：class MySimpleAgent(SimpleAgent)
```

教材展示了 `Agent` 和 `MySimpleAgent`，却省略了框架内部 `SimpleAgent` 的类定义，因此在正文里找不到 `class SimpleAgent(Agent)` 这一行。

教材 7.4.1 末尾说“通过继承 `Agent` 基类”，是在概括整个继承关系；**如果严格按照代码看，本节的 `MySimpleAgent` 直接继承的是 `SimpleAgent`。**

## 4. 7.4.5 的 FunctionCallAgent 如何定位？它与第四章的 Agent 范式有什么关系？

对应教材：**7.4.1 SimpleAgent**、**7.4.2 ReActAgent**、**7.4.3 ReflectionAgent**、**7.4.4 PlanAndSolveAgent**、**7.4.5 FunctionCallAgent**，并联系第四章的三种 Agent 范式，以及本章开头的安装版本说明。

### 疑惑

> 7.4提到7.4.1是新增简单agent类，7.4.2-7.4.4分别对应第四章的范式，那7.4.5呢？

### 解答

**（1）7.4.5 是从“工具怎样被调用”这个角度补充的一种 Agent 实现。**

**7.4.5 的 FunctionCallAgent，是从“工具怎样被调用”这个角度补充的一种 Agent 实现。** 它和 ReAct、Reflection、Plan-and-Solve 的分类角度有所不同。

可以分成两层理解：

| 关注的问题                     | 对应概念                                                                        |
| ------------------------------ | ------------------------------------------------------------------------------- |
| Agent 怎样组织任务处理过程？   | ReAct：思考与行动交替；Reflection：生成后反思改进；Plan-and-Solve：先规划再执行 |
| Agent 怎样表达和发起工具调用？ | 提示词约定文本格式，或使用模型接口提供的 Function Calling                       |

**（2）前面两节的实现，通过提示词约定格式，再解析模型生成的文本来调用工具。**

前面两节的实现，主要通过**提示词约定格式，再解析模型生成的文本**来调用工具：

- **7.4.1 的 MySimpleAgent**：解析 `[TOOL_CALL:search:查询内容]`。
- **7.4.2 的 MyReActAgent**：解析 `Action: search[查询内容]`。

**（3）FunctionCallAgent 使用原生 Function Calling 接口表达工具调用请求。**

**7.4.5 则使用原生 Function Calling 接口**：程序把工具名称、用途、参数结构传给模型，模型通过专门的结构化字段返回“调用哪个工具、传什么参数”。整体流程是：

```text
程序将问题和工具定义交给模型
            ↓
模型返回工具调用请求（名称、参数）
            ↓
Agent 的代码执行工具
            ↓
将工具结果传回模型
            ↓
模型继续请求工具，或给出最终回答
```

**（4）实际执行工具的仍然是 Agent 的代码。**

这里仍然是 **Agent 的代码实际执行工具**，模型负责生成调用请求。

**（5）ReAct 和 Function Calling 可以结合使用。**

所以，**ReAct 和 Function Calling 可以结合使用**：ReAct 组织“思考—行动—观察”的循环，Function Calling 承担其中工具调用的表达与交互。它们并不互斥。

**（6）7.4.5 属于后续版本扩展，需要留意教材中的版本差异。**

另外，[7.4.5 正文](<../../hello-agents/docs/chapter7/第七章 构建你的Agent框架.md#745-functioncallagent>)明确注明 FunctionCallAgent 是 **`0.2.8` 之后引入的**，属于后续版本扩展，因此没有像 7.4.2–7.4.4 那样直接对应第四章的实现。

本章开头的安装示例指定的是 `hello-agents==0.1.1`，而 7.4.5 讨论的是后续版本新增的能力。阅读和实践时，需要区分这两处版本，不能直接假定 `0.1.1` 已包含 FunctionCallAgent。

## 5. 7.4.1–7.4.5 的 Agent 类如何继承？它们是否还继承第四章的 Agent 类？

## 6. 如何理解 7.4.5 的对话接口、原生 Function Calling 与完整调用流程？

对应教材：**7.4.5 FunctionCallAgent**，联系第四章 `HelloAgentsLLM.think()` 的底层调用，说明普通对话与原生工具调用如何共用接口，并逐段解释工具定义、模型响应、框架封装及完整执行循环。

### 疑惑

> 7.4.5的代码不太懂，你再解释一下

> 原生 Function Calling 接口，指的是别人开发好的接口？

> 说明.md 6的“client.chat.completions.create”是什么？以及第6点有没有完整的例子？

> client.chat.completions.create请求和我们之前对话式的请求有什么区别吗？

### 解答

**`client.chat.completions.create(...)` 就是前面已经使用过的对话请求接口。原生 Function Calling 是这个接口支持的一种能力；区别主要在请求参数、返回格式，以及程序收到响应后的处理。**

下面先建立它与第四章的联系，再看 7.4.5 的代码，最后补上从定义工具到生成最终回答的完整示例。

**（1）client.chat.completions.create 是 SDK 中发起对话请求的方法。**

先看客户端的创建：

```python
from openai import OpenAI

client = OpenAI()
```

这里的 `client` 是 OpenAI Python SDK 的客户端对象，用来联系模型服务，本身不是大模型。

```python
client.chat.completions.create(...)
```

可以拆开理解：

| 部分             | 含义                                   |
| ---------------- | -------------------------------------- |
| `client`       | 通过`OpenAI()` 创建的 SDK 客户端对象 |
| `.chat`        | 访问客户端中的对话相关资源             |
| `.completions` | 访问生成对话响应的资源                 |
| `.create(...)` | 调用方法，发起一次生成请求             |

**前面的点号是在逐层访问对象，最后的 `create(...)` 才是在调用方法。**

它对应模型服务的 `POST /chat/completions` 接口；SDK 根据客户端配置的服务地址发送请求，并处理响应。使用 OpenAI 默认地址时，完整路径包含 `/v1/chat/completions`。[OpenAI 官方接口文档](https://developers.openai.com/api/reference/python/resources/chat/subresources/completions/methods/create)

这里的 `create` 指的是**生成一次响应**，不会创建一个新模型，也不会自动执行你电脑上的工具函数。

**（2）第四章的普通对话、提示词式工具调用和原生 Function Calling，可以使用同一个接口。**

第四章的 [HelloAgentsLLM.think()](../../hello-agents/code/chapter4/llm_client.py) 内部已经在使用：

```python
response = self.client.chat.completions.create(
    model=self.model,
    messages=messages,
    temperature=temperature,
    stream=True,
)
```

所以，之前写：

```python
llm.think(messages)
```

实际调用关系就是：

```text
你调用 llm.think(messages)
          ↓
HelloAgentsLLM 内部调用 client.chat.completions.create(...)
          ↓
模型服务处理请求并返回响应
```

区别主要在**发送哪些信息，以及怎样处理响应**。以下按非流式返回说明读取位置：

| 使用方式                   | 发给模型的信息                                           | 程序主要读取什么                                       |
| -------------------------- | -------------------------------------------------------- | ------------------------------------------------------ |
| 普通对话                   | `messages`：提示词、用户问题、历史消息                 | `message.content` 中的文本                           |
| 前面通过提示词实现工具调用 | 在`messages` 中说明工具及约定的指令格式                | `message.content` 文本中的 `[TOOL_CALL:…]` 等标记 |
| 原生 Function Calling      | `messages`，以及专门的 `tools`、`tool_choice` 参数 | 结构化的`message.tool_calls`，或普通文本回答         |

例如，假设 `model`、`messages` 和 `tools` 已经准备好，普通对话请求可以写成：

```python
response = client.chat.completions.create(
    model=model,
    messages=messages,
)
```

使用原生工具调用时，仍然调用同一个方法，只是增加了参数：

```python
response = client.chat.completions.create(
    model=model,
    messages=messages,
    tools=tools,          # 告诉模型有哪些工具及其参数
    tool_choice="auto",   # 允许模型决定是否请求工具
)
```

模型此时可能直接回答，也可能返回工具调用请求；如果返回工具请求，程序就需要执行工具、回传结果，再调用这个接口。[OpenAI 官方接口文档](https://developers.openai.com/api/reference/python/resources/chat/subresources/completions/methods/create)

普通对话、提示词式工具调用、原生 Function Calling，都可以通过同一个对话接口完成；工具调用方式不同，主要体现在请求参数、返回格式和程序后续处理上。

第四章中的 `stream=True` 表示“分批接收响应”，第四章代码会读取各个分片并拼接文本。**是否流式返回**与**是否使用原生工具调用**是两个不同的设置。下面的完整示例使用非流式请求，便于观察完整的响应对象。

**（3）原生 Function Calling 是模型服务商提供的接口能力，需要区分三个层次。**

**“原生 Function Calling”可以理解为：模型服务商已经开发并提供好的、支持工具调用的接口能力。** 在教材的例子中，提供方是 OpenAI。

不过，需要分清三个层次：

| 层次                                                 | 谁提供                     | 负责什么                                       |
| ---------------------------------------------------- | -------------------------- | ---------------------------------------------- |
| **原生 Function Calling 能力**                 | 模型服务商，例如 OpenAI    | 接收工具说明，让模型返回结构化的工具调用请求   |
| **FunctionCallAgent**                          | HelloAgents 框架的开发者   | 使用上述接口，组织模型请求、工具执行和结果回传 |
| **具体业务工具**，如 `get_current_weather()` | 你自己实现，或接入现成服务 | 真正查询天气、读取数据库、执行计算等           |

这里的 **“原生”**，强调的是：**工具调用已经是模型服务接口直接支持的一种能力**。你可以通过接口规定的 `tools` 参数提供工具说明，并从响应中的 `tool_calls` 读取调用请求。[OpenAI 官方文档](https://developers.openai.com/api/docs/guides/function-calling)

它通常体现在对话接口的参数和返回结果中。教材里的调用是：

```python
client.chat.completions.create(
    model="gpt-5",
    messages=messages,
    tools=tools,          # 按接口规定的格式提供工具说明
    tool_choice="auto"
)
```

这和前面自己约定：

```text
[TOOL_CALL:search:查询内容]
```

有所区别：前者使用服务商提供的工具调用格式；后者要求模型在普通文本里输出你约定的标记，再由你解析。

**但服务商提供了 Function Calling 能力，并不代表它已经实现了你的天气查询函数。** 模型可以返回“请调用 `get_current_weather`，参数是波士顿”，实际查询仍由你的程序完成。HelloAgents 的 `FunctionCallAgent` 就是在这套已有接口之上，把这些步骤封装起来。

这节代码容易看不懂，是因为教材把**“框架内部的封装方法”和“独立的 API 使用示例”放在同一个代码块里，而且没有展示完整的工具执行过程**。

理解原生接口后，我们先看教材后半段的天气例子，再回头理解 `_invoke_with_tools()`。

| 代码                                                 | 作用                                                         |
| ---------------------------------------------------- | ------------------------------------------------------------ |
| 上半段`def _invoke_with_tools(self, ...)`          | `FunctionCallAgent` 内部的方法片段，负责整理参数并请求模型 |
| 下半段`client = OpenAI()` 到 `print(completion)` | 绕过 Agent 框架，直接使用 SDK 发起一次请求的示例             |

**下半段没有调用上半段的方法。** 它们都使用了 `client.chat.completions.create(...)`，教材想通过这种对照展示：框架是在原生接口上再做封装。

**（5）下半段先创建客户端，再提供工具说明。**

先看下半段：

```python
from openai import OpenAI

client = OpenAI()
```

这里创建了一个 **OpenAI SDK 客户端对象**，用来向模型服务发送请求。它对应我们之前讨论的“联系模型的客户端”，本身不是大模型。

接下来很长的 `tools`，可以先理解为**给模型看的工具说明书**：

```python
tools = [
    {
        "type": "function",
        "function": {
            "name": "get_current_weather",
            "description": "Get the current weather in a given location",
            "parameters": {
                "type": "object",
                "properties": {
                    "location": {
                        "type": "string",
                        "description": "The city and state, e.g. San Francisco, CA",
                    },
                    "unit": {
                        "type": "string",
                        "enum": ["celsius", "fahrenheit"],
                    },
                },
                "required": ["location"],
            },
        },
    }
]
```

逐项翻译如下：

| 字段                              | 含义                                                        |
| --------------------------------- | ----------------------------------------------------------- |
| 最外面的列表`[...]`             | 可以提供多个工具，这里只提供一个                            |
| `"type": "function"`            | 这是一个函数工具                                            |
| `"name": "get_current_weather"` | 工具名称，模型请求调用时使用这个名字                        |
| `"description": ...`            | 告诉模型这个工具能查询某个地点的当前天气                    |
| `"parameters"`                  | 描述调用工具时可以传哪些参数                                |
| 参数中的`"type": "object"`      | 参数整体是一个对象，可以理解为一组键值对                    |
| `"properties"`                  | 列出参数字段，这里有`location` 和 `unit`                |
| `"type": "string"`              | 对应参数的值应该是字符串                                    |
| `"enum": [...]`                 | `unit` 的允许值是 `celsius` 或 `fahrenheit`           |
| `"required": ["location"]`      | 按这个定义，调用时必须提供`location`；`unit` 可以不提供 |

把它翻译成人话，就是：

> 我这里有一个叫 `get_current_weather` 的工具，可以查询当前天气。
> 使用时必须告诉我地点，也可以指定摄氏度或华氏度。

注意，**这一段只是描述工具，没有定义真正查询天气的 Python 函数。**

例如，下面这种函数实现，教材的示例里并没有提供：

```python
def get_current_weather(location, unit="celsius"):
    # 在这里调用天气服务，取得真实数据
    ...
```

工具的**说明**和工具的**实现**是两件事。

**（6）将问题和工具说明一起发送给模型。**

然后，程序准备用户的问题：

```python
messages = [
    {
        "role": "user",
        "content": "What's the weather like in Boston today?"
    }
]
```

这里的意思是：“用户问，波士顿今天天气怎么样？”

再把**问题和工具说明一起发送给模型**：

```python
completion = client.chat.completions.create(
    model="gpt-5",
    messages=messages,
    tools=tools,
    tool_choice="auto"
)
```

这四个参数可以这样理解：

- `model`：让哪个模型处理请求。
- `messages`：用户说了什么，以及已有的对话内容。
- `tools`：模型可以请求使用哪些工具。
- `tool_choice="auto"`：允许模型自己判断是否需要工具，也允许它直接回复。

`auto` 不意味着一定调用工具，也不意味着 SDK 会自动替你执行本地函数。[OpenAI 官方接口文档](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)

**（7）模型返回调用请求，程序再执行真实工具。**

在非流式请求中，`completion` 是响应对象，先取出模型的消息：

```python
message = completion.choices[0].message

# 普通文本回答
print(message.content)

# 工具调用请求列表
print(message.tool_calls)
```

`choices[0]` 表示取第一个候选结果。模型请求调用工具时，重点在 `tool_calls` 中，`content` 可能为空；不能只看文本为空就判断调用失败。

为了查看单条请求，可以这样取出第一个工具调用：

```python
if message.tool_calls:
    tool_call = message.tool_calls[0]
    print(tool_call.function.name)
    print(tool_call.function.arguments)
```

这里取第一条只是为了说明对象结构；完整示例会遍历并处理本轮全部工具请求。

**假设模型决定调用天气工具，它返回的重点是“调用请求”。**

下面是一个示意结果，不是实际查询结果：

```python
# 模型请求使用的工具名
tool_call.function.name
# "get_current_weather"

# 模型生成的调用参数，注意它是 JSON 字符串
tool_call.function.arguments
# '{"location": "Boston, MA", "unit": "celsius"}'
```

它表达的是：

> 请帮我执行 `get_current_weather`，地点是波士顿，单位用摄氏度。

此时还没有查天气。程序还需要解析参数，再执行真实函数。例如，**假设已经实现了对应的天气函数，并确认模型请求的就是它**：

```python
import json

arguments = json.loads(tool_call.function.arguments)

# arguments 现在是 Python 字典：
# {"location": "Boston, MA", "unit": "celsius"}

result = get_current_weather(**arguments)
```

最后一行的 `**arguments` 是把字典展开成关键字参数，相当于：

```python
result = get_current_weather(
    location="Boston, MA",
    unit="celsius"
)
```

拿到 `result` 后，程序还要把工具结果交回模型，让模型生成面向用户的回答。完整过程是：

```text
程序发送：用户问题 + 工具说明
                ↓
模型返回：工具名 + 调用参数
                ↓
程序执行：真正的天气查询函数
                ↓
程序发送：工具执行结果
                ↓
模型返回：基于查询结果的回答
```

这也是官方文档说明的工具调用流程。[OpenAI 官方 Function Calling 指南](https://developers.openai.com/api/docs/guides/function-calling)

**教材的下半段只做到了第一次模型请求，然后用 `print(completion)` 打印响应对象。它没有写出执行天气函数和回传结果的后续代码。**

**（8）上半段是框架内部的方法封装，先理解方法参数。**

理解这个原生示例以后，再看上半段的封装：

```python
def _invoke_with_tools(
    self,
    messages: list[dict[str, Any]],
    tools: list[dict[str, Any]],
    tool_choice: Union[str, dict],
    **kwargs
):
```

这是 `FunctionCallAgent` 的一个内部方法，教材省略了外层的 `class FunctionCallAgent(Agent):`。

参数含义是：

| 参数            | 含义                               |
| --------------- | ---------------------------------- |
| `self`        | 当前这个`FunctionCallAgent` 实例 |
| `messages`    | 要发送的消息列表                   |
| `tools`       | 要发送的工具说明列表               |
| `tool_choice` | 工具选择策略，例如`"auto"`       |
| `**kwargs`    | 收集调用者额外传入的关键字参数     |

其中：

```python
list[dict[str, Any]]
```

表示“一个列表，列表中的元素是字典，字典的键是字符串，值可以是不同类型”。

```python
Union[str, dict]
```

表示“这个参数可以是字符串，也可以是字典”。

这些都是**类型提示**，不会自动执行工具或解析 JSON。

**（9）从 HelloAgentsLLM 中取得底层客户端。**

接着看方法内部。

```python
client = getattr(self.llm, "_client", None)
```

先把三个对象分清：

```text
self                   当前的 FunctionCallAgent
  └── self.llm         它持有的 HelloAgentsLLM 对象
        └── _client    HelloAgentsLLM 内部的 SDK 客户端
```

`getattr(self.llm, "_client", None)` 的意思是：

> 从 `self.llm` 中读取 `_client` 属性；如果没有这个属性，就返回 `None`。

因此下面的代码是在检查有没有拿到客户端：

```python
if client is None:
    raise RuntimeError(
        "HelloAgentsLLM 未正确初始化客户端，无法执行函数调用。"
    )
```

拿不到客户端，就无法发送请求，于是报错。

这里 `_client`、`_invoke_with_tools` 开头的下划线，表示“供内部使用”的命名约定，并不是 Python 强制的私有权限。

**（10）通过 kwargs 和 setdefault 合并本次参数与框架默认配置。**

接下来这几行是在**整理本次请求的配置参数**：

```python
client_kwargs = dict(kwargs)

client_kwargs.setdefault(
    "temperature",
    self.llm.temperature
)

if self.llm.max_tokens is not None:
    client_kwargs.setdefault(
        "max_tokens",
        self.llm.max_tokens
    )
```

第一行：

```python
client_kwargs = dict(kwargs)
```

把额外参数复制到一个字典中，供后面补充默认值。

`setdefault()` 的规则是：

> **字典里已经有这个键，就保留原值；没有这个键，才填入默认值。**

例如，假设框架配置中的值是：

```python
self.llm.temperature = 0.7
```

如果调用者这次传入：

```python
kwargs = {"temperature": 0.2}
```

执行 `setdefault()` 后，仍然使用：

```python
{"temperature": 0.2}
```

如果调用者没有传：

```python
kwargs = {}
```

才会补成：

```python
{"temperature": 0.7}
```

所以这里实现的是：**调用者本次明确传入的参数优先，框架配置负责补默认值。**

`max_tokens` 采用同样的处理，只是先检查框架里有没有设置它。

这里解释的是教材的参数合并逻辑；具体模型支持哪些参数，需要按模型核对，官方接口也明确说明参数支持会因模型而异。[OpenAI 官方接口文档](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)

**（11）发送模型请求，并对照原生示例理解封装增加了什么。**

最后，这个方法真正发送请求：

```python
return client.chat.completions.create(
    model=self.llm.model,
    messages=messages,
    tools=tools,
    tool_choice=tool_choice,
    **client_kwargs,
)
```

你可以把它与下半段的直接调用对照：

| 原生示例                                | 框架封装                                      |
| --------------------------------------- | --------------------------------------------- |
| `client = OpenAI()`                   | 使用`self.llm._client` 中已经准备好的客户端 |
| `model="gpt-5"`                       | 从`self.llm.model` 读取模型名称             |
| 直接使用示例中的`messages`、`tools` | 接收调用者传入的`messages`、`tools`       |
| 写死`tool_choice="auto"`              | 接收调用者传入的`tool_choice`               |
| 示例没有额外配置                        | 合并本次参数和框架默认配置                    |

这里的：

```python
**client_kwargs
```

同样是字典展开。例如：

```python
client_kwargs = {"temperature": 0.2}
```

展开后，就相当于在调用中额外写了：

```python
temperature=0.2
```

**这个方法返回的是模型响应对象，后续还需要其他代码读取响应、执行工具和继续对话。** 方法注释里的“执行函数调用”，应当理解为“发起支持函数调用的模型请求”。

**（12）其他辅助方法分别处理工具调用流程中的不同环节。**

教材开头列出的其他辅助方法，就是在处理其中的不同环节：

| 方法                               | 负责什么                                                 |
| ---------------------------------- | -------------------------------------------------------- |
| `_build_tool_schemas`            | 根据工具的名称、描述和参数定义，生成发给模型的工具说明   |
| `_extract_message_content`       | 从模型响应中取出文本内容                                 |
| `_parse_function_call_arguments` | 把工具调用参数的 JSON 字符串解析成 Python 字典           |
| `_convert_parameter_types`       | 按工具参数定义尝试转换类型，例如将`"3"` 转成整数 `3` |
| `_invoke_with_tools`             | 整理请求参数，调用模型并返回响应                         |

它们需要由 `FunctionCallAgent` 的运行流程组织起来，才能完成“请求模型 → 执行工具 → 回传结果 → 继续请求”的循环。

**（13）完整示例：定义工具、请求模型、执行工具、回传结果并生成回答。**

前面的教材代码和逐段解读是片段：教材天气函数没有完整实现，原生示例只打印了第一次响应，也没有写出保存工具请求、回传结果和再次请求模型的代码。下面将这些环节补齐，可以保存为 `function_call_demo.py`。

这个例子包含完整流程：

```text
定义工具和工具说明
    ↓
向模型发送用户问题
    ↓
模型返回工具调用请求
    ↓
程序解析参数并执行工具
    ↓
把工具结果交回模型
    ↓
模型生成最终回答，或继续请求工具
```

这里的天气函数返回**模拟数据**；模型调用仍然使用真实 API。示例沿用教材的 `gpt-5`，使用 OpenAI 服务，需要配置可用的 OpenAI API 密钥。

先安装依赖：

```bash
pip install openai python-dotenv
```

在脚本同目录的 `.env` 中配置：

```dotenv
OPENAI_API_KEY=你的OpenAI_API密钥
```

`load_dotenv()` 加载环境变量后，`OpenAI()` 会读取 `OPENAI_API_KEY`。[OpenAI 官方 Python SDK 文档](https://developers.openai.com/api/reference/python)

完整脚本如下：

```python
import json

from dotenv import load_dotenv
from openai import OpenAI


# ---------- 1. 创建模型客户端 ----------

load_dotenv()
client = OpenAI()

MODEL = "gpt-5"


# ---------- 2. 实现真正会被程序执行的工具函数 ----------

def get_current_weather(
    location: str,
    unit: str = "celsius",
) -> dict:
    """返回模拟天气数据，演示工具调用流程。"""

    if not isinstance(location, str) or not location.strip():
        raise ValueError("location 必须是非空字符串")

    if unit not in ("celsius", "fahrenheit"):
        raise ValueError("不支持的温度单位")

    return {
        "location": location,
        "temperature": 20 if unit == "celsius" else 68,
        "unit": unit,
        "condition": "晴",
        "data_source": "模拟数据，不是真实天气",
    }


# ---------- 3. 编写给模型看的工具说明 ----------

tools = [
    {
        "type": "function",
        "function": {
            "name": "get_current_weather",
            "description": "获取指定地点的模拟天气，用于演示工具调用。",
            "parameters": {
                "type": "object",
                "properties": {
                    "location": {
                        "type": "string",
                        "description": "城市名称，例如 Boston",
                    },
                    "unit": {
                        "type": "string",
                        "enum": ["celsius", "fahrenheit"],
                    },
                },
                "required": ["location"],
            },
        },
    }
]


# ---------- 4. 准备初始对话 ----------

messages = [
    {
        "role": "system",
        "content": (
            "你是一个工具调用演示助手。"
            "请使用提供的工具获取天气数据，再回答用户。"
            "回答时必须明确说明数据是模拟数据。"
        ),
    },
    {
        "role": "user",
        "content": "请查询波士顿的模拟天气，使用摄氏度。",
    },
]


# ---------- 5. 模型请求与工具执行循环 ----------

for round_number in range(1, 5):
    print(f"\n--- 第 {round_number} 次调用模型 ---")

    # 请求模型：它可能返回文本，也可能返回工具调用请求
    completion = client.chat.completions.create(
        model=MODEL,
        messages=messages,
        tools=tools,
        tool_choice="auto",
    )

    message = completion.choices[0].message

    # 没有工具请求时，输出模型回答并结束
    if not message.tool_calls:
        print("最终回答：", message.content or "（本轮没有文本回答）")
        break

    # 先保存模型发出的工具调用请求
    # model_dump() 将 SDK 消息对象转换成字典
    messages.append(message.model_dump(exclude_none=True))

    # 一次响应可能包含多个工具调用请求
    for tool_call in message.tool_calls:
        tool_name = tool_call.function.name

        print("模型请求的工具：", tool_name)
        print("模型生成的参数：", tool_call.function.arguments)

        try:
            # 将 JSON 字符串转换为 Python 字典
            arguments = json.loads(tool_call.function.arguments)

            if not isinstance(arguments, dict):
                raise ValueError("工具参数必须是 JSON 对象")

            # 根据工具名称分发，执行实际的 Python 函数
            if tool_name == "get_current_weather":
                result = get_current_weather(**arguments)
            else:
                raise ValueError(f"未知工具：{tool_name}")

        except (ValueError, TypeError) as error:
            result = {"error": str(error)}

        print("工具执行结果：", result)

        # 把结果加入对话，供下一次模型请求使用
        messages.append(
            {
                "role": "tool",
                "tool_call_id": tool_call.id,
                "content": json.dumps(result, ensure_ascii=False),
            }
        )

    # 这一轮工具全部执行完毕后，回到循环开头再次调用模型

else:
    print("达到最大模型调用次数，尚未得到最终回答。")
```

保存后，在配置好依赖和密钥的 Python 环境中运行：

```bash
python function_call_demo.py
```

这段代码补齐了官方工具调用流程中的“程序执行函数”和“回传工具结果”两个环节。[OpenAI 官方 Function Calling 指南](https://developers.openai.com/api/docs/guides/function-calling)

它直接使用原生 SDK 展示工具调用循环，便于观察框架底层需要组织哪些步骤。`FunctionCallAgent` 则将这类循环、工具管理和消息处理封装成可复用的组件。

**（14）同一个 create() 会在不同轮次接收不同的上下文。**

第一次调用时，`messages` 中主要是：

```text
系统要求
用户问题
```

模型可能返回：

```text
请调用 get_current_weather
参数：{"location": "Boston", "unit": "celsius"}
```

程序执行工具后，第二次调用时，`messages` 已经包含：

```text
系统要求
用户问题
模型刚才发出的工具调用请求
工具执行结果：模拟天气，20°C，晴
```

所以，**第二次仍然调用同一个 `create()` 方法，但发送的上下文增加了工具结果**。模型现在可以据此生成最终回答。

这个对话状态由程序通过 `messages` 维护，因此代码必须先保存模型的工具请求，再添加对应的工具结果，而不是假定 API 自动记住上一轮。

其中：

```python
{
    "role": "tool",
    "tool_call_id": tool_call.id,
    "content": ...,
}
```

表示：

> 这是一条工具执行结果，它回答的是 `tool_call.id` 对应的那次调用请求。

`content` 是发给模型的结果字符串。示例用 `json.dumps(result, ensure_ascii=False)` 将 Python 字典转换成 JSON 字符串，便于模型读取，也保留中文内容。

典型情况下，这个例子会经历两次模型调用：第一次请求工具，第二次生成回答。但 `tool_choice="auto"` 允许直接回复或继续请求工具，所以代码使用循环处理，而没有写死“只调用两次”。一轮响应中可能有多个工具请求，示例会逐个处理后，再发起下一次模型请求；达到最大轮数时，会明确提示尚未得到最终回答。

这一节中的 `_invoke_with_tools()` 封装的是**单次 `create()` 请求**；完整的 `FunctionCallAgent` 还需要组织外层的循环、工具执行和消息更新。

## 7. 为什么 7.5.2 的图先执行工具，再调用 LLM？不应该先由 LLM 生成工具指令吗？

对应教材：**7.5.2 自定义工具开发**中的[图 7.1](../../hello-agents/docs/images/7-figures/01.png)及 `test_my_calculator.py`，并对照 **7.4.1 SimpleAgent** 中 `MySimpleAgent._run_with_tools()` 的完整工具调用流程。

### 疑惑

> 7.5.2的图不太懂，图里好像是调用工具获得计算结果，然后将结果交给llm思考，然后再输出最终答案。这个流程不太懂，不应该是工具llm的思考结果解析结果字符串，解析到工具指令再执行工具吗？

### 解答

**你理解的“先让 LLM 生成工具调用指令，再解析、执行工具”的流程是对的。7.5.2 的图对应的是一个简化演示：程序直接指定计算工具和表达式，计算完成后才让 LLM 组织回答。**

我对照了图和代码，区别主要在于：**谁决定调用哪个工具、传什么参数。**

**（1）7.5.2 中，工具和参数已经由程序写好了。**

看 [test_my_calculator.py](../../hello-agents/code/chapter7/test_my_calculator.py) 第 48 行：

```python
calc_result = registry.execute_tool(
    "my_calculator",
    "sqrt(16) + 2 * 3"
)
```

这里已经明确指定：

- 工具：`my_calculator`
- 参数：`sqrt(16) + 2 * 3`

**这两个字符串是开发者直接写在代码中的，没有经过 LLM 选择或生成。**

前面的：

```python
user_question = "请帮我计算 sqrt(16) + 2 * 3"
```

虽然保存了用户问题，但代码并没有让 LLM 从这个问题中提取表达式，而是又手动写了一遍表达式来调用工具。

因此，图中的 **②—⑤** 展示的是：

```text
程序指定计算任务
    ↓
ToolRegistry 找到对应工具
    ↓
计算工具执行 sqrt(16) + 2 * 3
    ↓
返回结果 "10.0"
```

**（2）图中后面的 LLM 调用，是为了把计算结果组织成自然语言回答。**

拿到计算结果后，代码才构造消息：

```python
final_messages = [
    {
        "role": "user",
        "content": (
            f"计算结果是 {calc_result}，"
            f"请用自然语言回答用户的问题：{user_question}"
        )
    }
]

response = llm.think(final_messages)
```

此时交给模型的信息相当于：

> 计算结果是 10.0，请用自然语言回答用户的问题：请帮我计算 sqrt(16) + 2 * 3。

模型就可以生成类似：

> 计算结果是 10，因为 √16 = 4，2 × 3 = 6，所以 4 + 6 = 10。

这对应图中的 **⑥—⑩**。

这里 `think()` 是模型调用方法的名字。**本次调用的用途是根据已有结果生成回答，并没有承担“决定调用哪个工具”的任务。**

对于这么简单的算式，程序直接输出 `10.0` 也可以；教材加上 LLM，是为了演示如何把工具结果用于回答生成。

**（3）你说的流程，才是前面 `MySimpleAgent` 展示的模型驱动工具调用流程。**

如果让模型自己决定如何处理同一个问题，流程应该是：

```text
用户：请帮我计算 sqrt(16) + 2 * 3
    ↓
第一次调用 LLM：提供问题和可用工具说明
    ↓
LLM 返回：工具调用指令，包括工具名和表达式
    ↓
Agent 的代码解析指令
    ↓
执行计算工具，得到 "10.0"
    ↓
把工具结果加入消息，再次调用 LLM
    ↓
LLM 根据结果生成最终回答
```

可以看到，**这里通常有两次模型调用，承担不同任务**：

| 模型调用 | 在这个例子中的作用                 |
| -------- | ---------------------------------- |
| 第一次   | 判断需要计算工具，生成工具调用请求 |
| 第二次   | 读取工具结果，组织最终回答         |

如果任务需要继续使用工具，第二次调用也可以返回新的工具请求，程序就继续循环。

前面 [MySimpleAgent 的 `_run_with_tools()`](../../hello-agents/code/chapter7/my_simple_agent.py)（第 81 行起）确实按这个顺序实现：

```python
# 先调用模型
response = self.llm.invoke(messages, **kwargs)

# 再解析模型响应中的工具调用标记
tool_calls = self._parse_tool_calls(response)

# 随后执行工具，把结果加入消息，再次调用模型
```

更准确地说，你提到的“解析 LLM 的思考结果”，是**解析模型返回内容中的工具调用指令**。例如，7.4.1 解析的是 `[TOOL_CALL:工具名:参数]`；并不是读取模型内部的思考过程。

**（4）这张图的标注确实容易让人混淆。**

图中把调度者标为 `SimpleAgent`，测试函数也叫 `test_with_simple_agent()`，但对应代码实际上：

- 没有创建 `SimpleAgent` 或 `MySimpleAgent` 实例。
- 没有调用 `agent.run(user_question)`。
- 只创建了模型客户端和工具注册表，然后手动安排执行顺序。

源码注释写的是“**模拟 SimpleAgent 使用工具的场景**”。

因此，阅读这张图时，应把它理解为 **7.5.2 用来验证自定义工具、并演示结果如何交给模型的简化流程**。它省略了你所说的“先调用 LLM → 解析工具指令”这一段，不能把它当作前面 `MySimpleAgent` 完整运行流程的展示。

# 第五章学习疑惑与解答

本文件整理阅读[第五章 基于低代码平台的智能体搭建](<../../hello-agents/docs/chapter5/第五章 基于低代码平台的智能体搭建.md>)时的疑惑及讨论结果。以下保留问答形式；前两组适当合并重复解释，第三组保留完整讨论内容，仅整理措辞和排版。

## 1. Coze、Dify 与 Codex、Cursor 有什么区别和联系？

**问：第五章介绍的 Coze、Dify 等，与 Codex、Cursor 有什么区别或联系？是否可以理解为：Coze、Dify 是搭建 Agent 的平台或工具，而 Codex、Cursor 是已经搭建好的 Agent？**

**答：** 在当前的学习语境下，**这样理解基本准确**：Coze、Dify 更侧重让你搭建并运行自己的智能体应用；Codex、Cursor 的 Agent 能力则让你直接使用一个已经具备工具和执行能力的智能体，协助完成开发等任务。

这里的 Codex 指智能体产品，而不是把它理解成单独的底层模型。严格来说，**Cursor 是包含 Agent 能力的开发工具，不能把整个 Cursor 完全等同于一个 Agent。** 这两类产品的能力也有交集，下面区分的是它们在任务中通常扮演的角色。

### （1）核心区别：搭建自己的智能体，还是使用现成的智能体

| 对比角度 | 第五章中的 Coze、Dify | Codex、Cursor 的典型开发用法 |
| --- | --- | --- |
| 主要用途 | 搭建、配置和运行智能体应用 | 使用现成的智能体协助完成任务 |
| 主要操作 | 配置提示词、知识库、工具，连接工作流节点 | 提出目标、提供项目上下文，让智能体读写文件和运行命令 |
| 典型产物 | 客服机器人、知识库助手、自动化工作流 | 代码修改、测试、文档，也可以是完整应用 |
| 流程组织 | 你设计工作流，也可以让其中的 Agent 节点动态决策 | 智能体通常根据目标与工具结果动态推进，你可以指导和约束 |
| 服务最终用户 | 平台提供应用发布、API 等能力 | 生成的应用需要有自己的运行和部署方式 |

例如：

> 用 Dify **搭建一个客服 Agent**；让 Codex **帮你编写这个客服 Agent 的代码或工具接口**。

Coze、Dify 的官方文档包含应用构建与发布能力；Codex、Cursor 的官方文档包含文件编辑、命令执行等开发能力。这些定位是理解它们的起点，不是互斥的能力边界。[Coze 文档](https://docs.coze.cn/developer_guides_coze_api_overview)、[Dify 文档](https://docs.dify.ai/en/home)、[Codex 官方文档](https://learn.chatgpt.com/docs/codex/cli)、[Cursor Agent 文档](https://cursor.com/docs/agent/overview)

### （2）例子：开发一个游戏攻略助手

假设你希望玩家可以问：“这个 Boss 怎么打？我现在的装备够不够？”

使用 Coze、Dify 时，可以配置这样的应用流程：

```text
玩家提出问题
    ↓
检索游戏攻略知识库
    ↓
需要时调用工具，查询装备或角色数据
    ↓
模型结合资料生成建议
    ↓
向玩家返回回答
```

你主要设计使用哪些资料、接入哪些工具、数据怎样传递，以及回答遵守什么规则。配置并发布后，由平台运行这个应用。

使用 Codex、Cursor 时，则可以提出：“帮我开发一个游戏攻略助手，需要聊天界面、攻略检索和角色数据查询。”它们可以协助编写前端、后端和工具接口，并运行测试、修复问题。

**帮助你开发的智能体，与开发完成后给玩家使用的攻略助手，是两个不同的角色：**

```text
开发时：你 → Codex / Cursor → 编写和修改攻略助手的程序

运行时：玩家 → 攻略助手程序 → 检索资料、调用模型和工具 → 回答
```

在这种开发方式下，玩家使用程序时，一般不需要继续打开你开发时使用的 Codex 或 Cursor 会话。

### （3）与第四章的联系：模型、工具、上下文和控制流程

这些智能体都可以借助第四章的概念理解：模型根据任务和上下文决定行动，程序调用工具，再把结果提供给模型继续处理。区别之一在于具体接入什么工具：

| 智能体 | 工具举例 |
| --- | --- |
| 第四章的搜索助手 | 搜索网页 |
| 游戏攻略助手 | 检索攻略、查询角色数据 |
| 编程智能体 | 读取文件、搜索代码、修改文件、运行测试 |

例如，编程智能体可能经历“读取报错 → 查看代码 → 修改 → 运行测试 → 根据失败结果继续修改”。可以用 ReAct 的“行动—观察—调整”来理解这种行为，但不能据此认定产品内部直接采用了教材中的简化实现。

还要区分：**在平台上画好的固定工作流，不自动等于 Plan-and-Solve。** 前者的步骤由你事先设计，第四章后者的计划由模型根据问题生成。平台也可以承载动态规划，但需要具体设计。

### （4）它们可以配合使用

对于游戏攻略助手，一种可行的组合是：

- 用 Dify 编排“攻略检索 → 模型回答”的流程。
- 用 Codex、Cursor 协助开发游戏角色数据查询接口。
- 再协助编写聊天页面和后端，由后端调用 Dify 应用 API。

运行时的结构可以是：

```text
玩家 → 你的网站与后端 → Dify 工作流 → 模型、知识库、游戏数据接口
```

这是基于上述能力的一种架构示例。Dify 官方提供了从自有后端调用已发布应用的 API 方式。[Dify API 文档](https://docs.dify.ai/en/api-reference/guides/get-started)

结合教材，可以这样理解三者的关系：**第四章学习用代码组织智能体，第五章学习用平台组件组织智能体，Codex、Cursor 则可以作为开发协作者，帮助你完成这两种方式中的工作。**

## 2. 现实中哪些是 LLM，哪些是 Agent？GPT、ChatGPT 和 Codex 应该怎样区分？

**问：Codex CLI 算 Agent 吗？Codex 的桌面版、CLI 版、VS Code 插件版是否都是 Agent，而裸 LLM 就是通过 API 请求的模型？以 GPT 系列为例，现实中哪些名称指 LLM，哪些指 Agent？**

**答：** 首先，**“智能体”就是 Agent 的中文名称，两者指同一个概念。** 其次，LLM、Agent、CLI 和 API 描述的是不同层面的东西，不能只按“有没有界面”或“是不是通过 API 调用”来分类。

### （1）先把现实中的名称对应起来

| 你看到的名称 | 属于什么 | 怎样理解 |
| --- | --- | --- |
| GPT-4、GPT-4o、GPT-4.1、GPT-6.1 Sol 等 | 模型（LLM／多模态模型） | 提供理解、推理和生成能力，可以作为 Agent 的核心组件 |
| ChatGPT | 面向用户的 AI 助手产品，包含 Agent 能力 | 你实际使用的网站或应用，里面使用模型，也可以配合工具完成任务 |
| Codex | Agent 产品／系统 | 把模型、文件操作、命令执行等能力组织起来，完成开发等任务 |
| Codex CLI、Codex 的 IDE 插件、桌面端入口 | 使用 Codex Agent 的客户端或入口 | 分别通过终端、编辑器、桌面界面与 Agent 交互 |

**这些 GPT 型号都属于模型。模型之间有能力和适用场景的差异，但不会因为某个模型更适合驱动 Agent，它本身就变成完整的 Agent。**

上面的模型名称用于说明分类，不表示所有历史型号都仍在各产品中提供。具体可用型号会随版本和账号而变化。官方文档将 Codex 定义为编程 Agent，将 Codex CLI 定义为运行 Codex 的终端客户端。[GPT-4.1 模型文档](https://developers.openai.com/api/docs/models/gpt-4.1)、[模型列表](https://learn.chatgpt.com/docs/models)、[官方术语表](https://learn.chatgpt.com/docs/glossary)

**GPT 和 ChatGPT 不是同一个概念：GPT-4.1 是模型名称，ChatGPT 是使用模型为你提供服务的产品。** 在产品中选择模型，可以理解为选择负责推理和生成的核心组件。

ChatGPT 也不只是裸模型的聊天窗口。它可以结合搜索、文件和其他工具工作；其中承担多步任务、持续使用工具的功能，就体现了 Agent 能力。不能因为某次只进行简单问答，就把整个产品等同于裸 LLM。[ChatGPT 官方介绍](https://learn.chatgpt.com/docs/use-chatgpt)

### （2）LLM 是组件，Agent 是组织这些组件来完成任务的系统

在本教程讨论的、基于大语言模型的 Agent 中：

- **LLM：** 根据输入理解任务、进行推理，生成回答、代码或工具调用请求。
- **工具：** 实际读取文件、修改代码、查询数据、运行命令等。
- **控制程序：** 组织模型调用、执行工具、维护上下文，并把工具结果交回模型，使任务继续推进。

以 Codex 为例，可以用下面的简化结构理解：

```text
你
 ↓
使用入口：桌面界面 / CLI / VS Code 插件
 ↓
Codex Agent 系统
 ├─ GPT 模型：理解、推理、生成回答或行动指令
 ├─ 工具：读取文件、修改代码、运行命令
 └─ 控制程序：执行指令、保存上下文、把结果交回模型
```

**LLM 和 Agent 不是两种互不相干的产品：LLM 可以是 Agent 内部的核心组件。** 因此，“我正在使用 Codex Agent”和“它使用某个 GPT 模型”可以同时成立。

### （3）同样是修复代码，直接调用模型和使用 Agent 有什么不同？

只调用一个 GPT 模型，可以是：

```text
你把代码和报错发给模型
    ↓
模型返回修改建议或新代码
    ↓
你自己保存文件、运行测试
```

这里使用的是模型的生成能力，执行工作由你完成。

让 Codex Agent 修复，则可以是：

```text
你告诉 Codex：“修复这个项目的报错”
    ↓
Codex 用模型分析任务
    ↓
通过工具读取文件、修改代码、运行测试
    ↓
把测试结果交给模型分析
    ↓
继续修改，或报告完成
```

第二种情况里，模型仍然存在，只是成为了 Agent 系统的一部分。**即使模型能生成工具调用请求，真正执行工具、传回结果的仍然是外部程序。** 这与第四章 `ReActAgent` 和 `ToolExecutor` 的分工相对应。

### （4）为什么不能用 CLI 或 API 来判断是不是 Agent？

**CLI（Command-Line Interface）是命令行界面，描述的是操作软件的方式。** Codex CLI 提供 Agent 能力，但普通命令行工具并不因此就是 Agent：

| 例子 | 如何理解 |
| --- | --- |
| `git`、`pip` | 普通命令行工具，主要执行你指定的命令 |
| Codex CLI | 通过命令行使用 Codex Agent 的客户端 |
| Codex 的桌面端、IDE 插件入口 | 通过图形界面或编辑器使用 Agent 能力 |

各入口的界面、运行环境和具体功能可能不同，但是否属于 Agent，要看系统如何组织和执行任务，不能看它是否运行在终端中。[Codex CLI 官方文档](https://learn.chatgpt.com/docs/codex/cli)

**API 是程序之间交互的方式，也不是裸 LLM 的专属标志：**

- Agent 内部经常通过 API 调用 LLM。
- 完整的 Agent 服务同样可以通过 API 提供给其他程序调用。
- 对于可本地运行的模型，也可以在本地加载使用，不一定通过网络 API。

因此，“Codex 各版本提供 Agent 能力”基本正确；“只要通过 API 调用，就是裸 LLM”则不正确。需要看 API 背后提供的是模型生成能力，还是包含工具执行和任务控制的完整服务。

**模型名称说明使用哪个核心组件；Agent 名称说明使用哪个任务执行系统；桌面端、CLI、插件说明从哪里操作；API 说明程序之间怎样交互。**

## 3. 有了 Codex、Cursor、Claude Code 等 Agent，Coze、Dify 是否就不太需要了？

**问：现在有了 Codex、Cursor、Claude 等 Agent 产品，而且它们背后的公司也有自己的 LLM，是不是就不太需要 Coze、Dify 了？或者说，Coze、Dify 的竞争力已经大打折扣？**

**答：** 你的判断有道理：**现成 Agent 越强，Coze、Dify 在某些场景下就越不必要，尤其是个人任务和简单原型。但不能直接推导出它们整体已经失去竞争力。**

前面把它们分成“搭建 Agent 的平台”和“现成 Agent”，是为了帮助理解。**实际市场里，这两类产品正在相互扩展，边界并不固定。**

另外，这里说的 Claude，如果指编程 Agent，更准确的名称是 **Claude Code**；Cursor 目前也有自己的 Composer 模型，同时支持其他厂商的模型。因此，“有没有自家模型”不是判断这些产品能否相互替代的唯一标准。[Claude Code 官网](https://claude.com/product/claude-code)、[Cursor 模型文档](https://cursor.com/docs/models/cursor-composer-2-5)

### （1）竞争压力之一：用户可以直接让现成 Agent 完成任务

用户可以直接让现成 Agent 完成任务，不必先搭一个专用 Agent。

例如，你只是想：

> “读取这几份资料，整理一份游戏行业报告。”

如果现成 Agent 已经能读取资料、搜索和生成报告，你可能直接交给它就够了。专门在 Dify 中配置知识库、连接节点、调试流程，反而增加了准备工作。

### （2）竞争压力之二：Agent 降低了直接写代码的成本

**Agent 降低了直接写代码的成本，削弱了低代码平台“少写代码”的优势。**

过去你可能觉得：

> “自己开发太难，所以用拖拽节点的平台。”

现在可能变成：

> “让 Codex 帮我开发，再由我检查和维护。”

所以，**如果一个平台的价值主要是“把几次模型调用连起来”，它受到的替代压力确实很大。** 这是基于能力变化的分析，并不是已经证实的市场份额结论。

### （3）完成一次任务，与提供持续运行的业务系统，有不同的要求

**“帮我完成一次任务”和“提供一个持续运行的业务系统”，还有不同的要求。**

仍以游戏攻略助手为例：

| 你的需求 | 主要需要解决什么 |
| --- | --- |
| 我自己查一次 Boss 攻略 | 找到资料，给出有用回答 |
| 做一个让玩家反复使用的攻略助手 | 接入游戏网站、更新知识库、管理会话、查看失败日志、调整流程、持续部署维护 |

后者除了模型能力，还需要一套应用运行和管理设施。

Dify 提供知识库、工作流、应用 API、运行日志，以及云端和自行部署的选择。这些能力可以减少团队自行搭建的工作。[Dify 官方文档](https://docs.dify.ai/en/home)、[日志文档](https://docs.dify.ai/en/cloud/use-dify/monitor/logs)

**Codex 当然也可以帮助开发这些设施，但“能开发出来”与“使用已有平台是否更省事”是两个问题。** 还要比较后续维护、业务人员能否修改、部署要求和总成本。平台也不是自动保证可靠，仍然需要设计和验证。

### （4）平台的这些优势也不是永远独占的

**这部分优势也不是平台永远独占的。**

模型厂商也在提供可嵌入应用的 Agent 运行能力。例如，OpenAI 的 Agents API 已经提供托管的 Codex 执行框架，处理会话、任务编排和恢复等工作。因此，竞争已经延伸到应用基础设施，而不只是聊天界面。[OpenAI Agents API 文档](https://developers.openai.com/api/docs/guides/agents-api/overview)

与此同时，Coze 也在改变。当前官方介绍中的“扣子编程”，已经包含通过自然语言开发智能体、工作流和全栈应用的能力，同时保留低代码方式。**它已经不能完全用教材中的“拖拽节点平台”来概括。**[扣子编程官方介绍](https://docs.coze.cn/guides_welcome)

### （5）不同类型的平台价值，受到的影响不同

因此，对竞争力的判断是：

| 平台提供的价值 | 面临的压力 |
| --- | --- |
| 简单聊天机器人、提示词封装、少量模型调用串联 | 容易被现成 Agent 或 AI 生成的代码替代 |
| 仅以“不会编程也能搭建”为卖点 | 优势会被 AI 编程持续削弱 |
| 已有业务集成、知识库管理、可视化维护、部署和运行管理 | 仍可能节省大量工作，但要与其他方案比较 |
| 针对具体行业积累的数据、流程和实际效果 | 价值更依赖业务积累，不能只靠更强的通用模型替代 |

### （6）这对学习第五章意味着什么？

**对当前的学习来说，不必把“熟练使用 Coze、Dify”当作构建 Agent 的必经之路。** 第五章更值得掌握的是节点输入输出、工具接入、知识库、状态传递、流程控制和发布运行这些概念。

理解之后，就能判断：某个任务直接交给现成 Agent 即可，还是值得做成平台工作流，或者用代码开发成独立应用。
